# 1. プロジェクト概要

## アプリ名

**決済オプティマイザー**（リポジトリ名 `kessai-optimizer`、表示名は `index.html` の `<title>` および PWA manifest の `name`）

- PWA short_name: `決済最適化`
- iOS ホーム画面表示名: `決済最適化`

## このアプリが何をするものか

店舗名を入力すると、**ユーザーが登録した決済手段の中から、還元率／還元額の高い順に「目安」を提示する**Webアプリ。

各候補には内訳（計算式）が付く。例：

```
PayPay                    2,000円  4.0%
  ← PayPayカード からチャージ
  基本 0.5% ＋ チャージ 0.5% ＋ イベント 3.0%（上限）
```

## 想定ユーザー

**単一ユーザー（このリポジトリのオーナー）を主対象とした個人用ツール。** [確認済み: サーバーなし・ログインなし・ユーザーデータは端末内のみという設計]

オーナーの属性（開発体制に直結するため重要）:

- **プログラミング完全未経験。** コードを読んで正しさを判断できない
- **iPadのブラウザのみで開発。** 手元でコマンドを実行できない
- 検証手段は「**テストが通ること**」と「GitHub上の自動チェックの色（緑／赤）」のみ

これは `CLAUDE.md` に明記された前提であり、本プロジェクトのあらゆる技術判断の根拠になっている。

## 解決しようとしている問題

**「普段行かない店に入ったとき、手持ちのどれで払うのが一番得か分からない」** という問題。

重要なのは利用場面の想定である。`CLAUDE.md` に明記されているとおり:

> 主な利用場面は **「普段行かない店に入ったとき」**。
> 毎日使うアプリではなく、辞書のように「必要なときに引く」もの。

この前提から導かれる設計上の含意:

- **常駐・通知・履歴収集の類は不要**（実際、作っていない）
- **店舗データは広く**必要（知らない店を引くため）
- **カードデータは狭くてよい**（自分が持っているものだけ）
- 起動から結果まで数タップで終わる導線が要る

## 最終的に目指している完成形

[確認済み: `CLAUDE.md` および会話での合意]

- 店舗名を入れると、手持ちの決済手段が還元率順に内訳付きで並ぶ
- 通信せず端末内で完結。位置情報・利用履歴・登録カードを外部送信しない
- ホーム画面に追加してアプリのように使える（PWA）
- 還元条件が変わったとき、**JSONファイルの書き換えだけで反映**できる
- 将来 React Native へ移植する可能性がある（そのため `src/core/` を独立させている）

**明示的に対象外とされているもの**（`CLAUDE.md` の「対象外（作らないもの）」）:

- 証券口座・クレカ積立に関する機能
- ログイン、アカウント、サーバー同期
- 家計簿アプリとのAPI連携

## 個別の説明

### `CLAUDE.md` — **最重要**

開発方針と4つの「設計上の絶対ルール」を記載。**変更前に必ず読むこと。** 内容の要旨:

1. `src/core/` にUIコードを入れない（React・DOM・localStorage・ブラウザAPI禁止）
2. 還元率データをコードに書かない（すべて `public/data/` のJSONから読む）
3. 通信しない（位置情報・利用履歴・登録カードを外部送信しない）
4. 数値は「目安」として扱う（0.1%単位に丸め、**実際より高く見積もらない**）

進め方として「一度に複数の変更をせず、1つずつ確認を取りながら進める」「`src/core/` を変更したら必ずテストを書き、通ることを確認してから報告する」「作業後は専門用語なしで説明する」も明記されている。

### `vite.config.ts`

3つの役割を兼ねる:

1. **base の切り替え** — `process.env.GITHUB_PAGES === 'true'` のとき `/kessai-optimizer/`、それ以外は `/`。GitHub Pages のプロジェクトサイトはサブパス配信になるため
2. **PWA設定** — manifest、Service Worker、precache 対象
3. **Vitest設定** — `defineConfig` を `vitest/config` から import している点に注意

### `public/data/*.json`

**このアプリの中身そのもの。** 各ファイル冒頭に `_note` フィールドがあり、編集者向けの注意書きが入っている（型では optional、計算には使われない）。

### `src/core/`

**React Native へ移植する際にそのまま持っていく想定の領域。** ブラウザ固有のものを一切含まない。この制約は `noUiDependency.test.ts` が機械的に強制している。

### `src/lib/`

`src/core/` に置けないもの（fetch・localStorage・現在時刻）の置き場。**core と UI の間の緩衝地帯。**

## コンポーネント間の関係

**`App.tsx` が唯一の状態保持者。** 3つの子コンポーネントはすべて「props を受け取り、変更を callback で親に返す」だけの制御コンポーネント。子同士は直接通信しない。

| コンポーネント | 受け取るもの | 返すもの | 自前の状態 |
| --- | --- | --- | --- |
| `StoreSearch` | `stores`, `selected` | `onSelect(store \| undefined)` | 入力文字列 `query` のみ |
| `PaymentSettings` | `cards`, `owned` | `onChange(owned)` | なし |
| `RewardList` | `results`, `cards`, `amount` | なし（表示専用） | 開いている内訳 `openId` のみ |

**意図的な設計**: 状態を一箇所に集めることで、データフローを単方向に保っている。Redux 等の状態管理ライブラリは導入していない（規模に対して過剰なため）。[推測: 明示的に議論はしていないが、依存を最小に保つ方針と整合する]

## データフロー

```
① 起動時（App.tsx の useEffect）
   loadOwnedPayments() → localStorage から決済手段を復元 → setOwned
   loadPaymentData()   → 3つのJSONを並行fetch → setData
                       → 失敗したら setLoadError（画面全体をエラー表示に）

② 店舗の検索（StoreSearch 内）
   入力 → useMemo(() => searchStores(stores, query)) → 候補リスト
   候補をタップ → onSelect(store) → App の store 状態が更新される

③ 結果の計算（App.tsx の useMemo）
   依存: [data, store, amount, owned]
   estimateRewards(data, { storeId, amount, owned, date: todayString() })
   → RewardBreakdown[]（お得な順にソート済み）

④ 決済手段の変更（PaymentSettings）
   onChange(next) → App の updateOwned()
   → setOwned(next) かつ saveOwnedPayments(next)（localStorage へ即時保存）
```

**注意**: `estimateRewards` は `useMemo` の中で毎回同期実行される。純粋関数なので副作用はない。データ量（カード数十件×店舗100件程度）では性能上の問題はない。[確認済み: 実測はしていないが、O(カード数 × 優遇数) の単純ループ]

## 状態管理

React の `useState` / `useMemo` / `useEffect` のみ。**外部の状態管理ライブラリは使っていない。**

`App.tsx` が持つ状態:

| 状態 | 型 | 説明 |
| --- | --- | --- |
| `data` | `PaymentData \| undefined` | JSONから読み込んだデータ一式。`undefined` は読み込み中 |
| `loadError` | `string \| undefined` | 読み込み失敗時のメッセージ |
| `owned` | `OwnedPayment[]` | 登録した決済手段 |
| `store` | `Store \| undefined` | 選択中の店舗 |
| `amountText` | `string` | 金額の入力文字列（数値ではなく文字列で保持） |
| `settingsOpen` | `boolean` | 決済手段の設定を開いているか |

**`amountText` を文字列で保持しているのは意図的。** 入力途中の状態（空欄、`-`、`1.` など）を素直に扱うため。`parseAmount()` で数値化し、不正なら `undefined`（＝未入力扱い）にしている。

## API通信

**なし。** 唯一の `fetch` は自分自身の静的JSONを読むもの。

```

値:   OwnedPayment[] を JSON.stringify したもの
```

`loadOwnedPayments()` は**壊れたデータに耐える設計**になっている:

- `try/catch` で囲む（プライベートブラウズ等で localStorage が使えない場合に備える）
- `JSON.parse` の結果が配列でなければ `[]` を返す
- 各要素について `cardId` が文字列であることを確認し、満たさない要素は捨てる

`saveOwnedPayments()` も `try/catch` で囲まれており、**保存に失敗しても画面は動き続ける。**

# 8. 設計上の重要な判断

**このセクションはコードを読んでも分からない情報を含む。変更前に必ず読むこと。**

## 8-1. データ構造は「案B（対象を店／分類で指定）」

**何を決めたか**: 優遇情報の対象を `{ kind: 'store', id }` または `{ kind: 'category', id }` で指定する。

**なぜその方式か**:
- 「コンビニ全般で+1%」のような制度を**1行**で書ける
- 実際の還元制度も「対象カテゴリ」で説明されることが多く、公式サイトの記載を写しやすい
- 追加される判断ルールは「細かい指定が勝つ」の一点のみで、テストで守れる

**他にどんな案があったか**:

| 案 | 内容 | 不採用の理由 |
| --- | --- | --- |
| **案A** | カード×店舗の組み合わせを1行ずつ書く表形式 | 「コンビニ全般」が書けず、対象店舗を1件ずつ複製する必要がある。**条件変更時の更新漏れが必ず起きる**（例：セブンだけ直してローソンを忘れる）。オーナーが手でJSONを保守する前提では致命的 |
| **案C** | 還元を「効果のリスト」として持ち、当てはまるものを合成する積み木モデル | 表現力は最も高い（三重取り・複数上限・複雑な条件）。しかし**概念が抽象的で、プログラミング未経験のオーナーが手でJSONを書くのが困難**。計算ロジックも最も長くなり、テストが増える＝「テストが通れば安心」と言える範囲が相対的に狭まる。用途（普段行かない店で目安を引く）に対して過剰 |

**補足**: 案Cの発想のうち「複数の効果を足し合わせる」部分は、後の判断8-3で**部分的に採用**している。案Cを全面否定したわけではない。

## 8-2. 還元率は「0.1%を1とする整数」

**何を決めたか**: `RewardRate = number`。ただし値の意味は**0.1%単位の整数**。1.0% → `10`、0.5% → `5`、7% → `70`。

**なぜその方式か**:
- 小数だと `0.1 + 0.2 = 0.30000000000000004` のような浮動小数点の誤差が出る
- `CLAUDE.md` に「0.1%単位に丸める」と既に決まっており、整数表現と完全に一致する
- 還元額の計算は `amount * rate / 1000` で済む（`RATE_SCALE = 1000`）

**他案**: 小数（`1.0`）で持つ案。誤差の懸念から不採用。

**注意**: `dataIntegrity.test.ts` が `Number.isInteger` を検査しているため、小数を書くとテストが落ちる。

## 8-3. 優遇は「置き換え」ではなく「足し合わせ」

**何を決めたか**: 当てはまる優遇の還元率を**すべて加算**する。基本 0.5% ＋ 特約店 1.0% ＋ イベント 1.0% ＝ 2.5%。

**なぜその方式か**: オーナーの明示的な要望。「各店舗で検索したとき、カード一覧で簡素な計算式を見れるようにしたい」。**内訳を見せることがアプリの価値の一部**という判断。

**経緯**: 当初は「優遇が基本還元率を置き換える」方式で実装していた（コミット `deabff5`）。オーナーの要望を受けて `261206a` で足し合わせ方式に変更した。**現在のコードに置き換え方式の名残はない。**

**他案**: 置き換え方式（有利な方を1つだけ採用）。安全側に倒れるが、内訳の式を作れないため不採用。

## 8-4. `rateBasis`（`add` / `total`）で数字の意味を明示する

**何を決めたか**: 各優遇に `rateBasis` を持たせ、`rate` の意味を明示させる。

- `'add'` — 基本還元率への**上乗せ分**（公式が「+1%」と書いている場合）
- `'total'` — 基本還元率を**含んだ合計**（公式が「最大7%（基本0.5%含む）」と書いている場合）

`'total'` のとき、上乗せ分は `max(0, rate - card.baseRate)` で求める。

**なぜその方式か**: **公式サイトの書き方が2通りあるため。** これを区別しないと、「合計7%」をそのまま足して基本の0.5%を二重計上する（＝過大評価）。オーナーが公式ページの数字を**そのまま写せる**ようにし、引き算はアプリ側で行う設計にした。データ入力の誤りを構造的に減らすための判断。

**他案**: 常に上乗せ分で書かせる案。オーナーが毎回引き算する必要があり、間違いやすいため不採用。

**関連する安全装置**: `dataIntegrity.test.ts` が「`total` 指定なのに基本還元率を下回る値」を検出する（上乗せ分がマイナスになる誤り）。

## 8-5. 特約店の上乗せは最大1つ、店指定が分類指定に勝つ

**何を決めたか**: `kind: 'merchant'` の優遇は**1つだけ**採用する。店を名指しした指定があればそれを使い、なければ分類の指定を使う。

**なぜその方式か**: 「コンビニ全般で+1%」と「セブンで+3%」の両方を足すと、実際より高く見積もることになる。

**同点時の扱い**: 同じ強さ（同じ specificity）の優遇が複数ある場合、**最も低い還元率を採用する**（`pickMerchantBonus` の `reduce`）。

```ts
return pool.reduce((lowest, bonus) =>
  toAddedRate(bonus, card) < toAddedRate(lowest, card) ? bonus : lowest,
)
```

これは `CLAUDE.md` の「実際より高く見積もらない」に従った安全側の選択。そもそも重複は `dataIntegrity.test.ts` が防いでいるため、**この分岐は保険**である。

**注意**: `kind: 'campaign'` は**すべて加算される**。merchant と campaign で挙動が異なることを理解しておくこと。

## 8-6. 端数は切り捨て

**何を決めたか**: 還元額の1円未満は `Math.floor` で切り捨てる。表示用の `formatRate` も切り捨て。

**なぜその方式か**: 四捨五入すると実際より多く見せることになる。`CLAUDE.md` の「実際より高く見積もらない」に従う。

## 8-7. 出典は「還元率の主張」にのみ必須

**何を決めたか**:

| データ | 出典 | 理由 |
| --- | --- | --- |
| 優遇（`Bonus`） | **必須** | 還元率の主張そのもの |
| チャージ元（`ChargeSource`） | **必須** | 還元率の主張 |
| カード（`Card`） | **必須。ただし現金（`kind: 'cash'`）のみ省略可** | 現金の0%には公式ページが存在しない |
| 店舗（`Store`） | **任意** | 店名と分類は「数値の主張」ではない |

**なぜその方式か**: 当初はすべてのデータに出典を必須にする方針だった（オーナーの要件）。しかし店舗97件について**検証できない公式URLを書くこと自体が不正確**であるため、店舗のみ任意に変更した。この変更はオーナーに説明済み。

**型の変更**: `Card.source`, `Store.source`, `RewardPart.source` を optional にした。`Bonus.source` と `ChargeSource.source` は必須のまま。

## 8-8. 仮の数値を置かない

**何を決めたか**: 確認できていない還元率をデータに入れない。サンプルであっても置かない。

**なぜその方式か**: 開発初期は構造確認のため架空の還元率を入れていた（楽天カード1%、三井住友NLコンビニ7%など）。しかしオーナーが実際にアプリを使い始める段階で、**間違った数字が表示されているほうが危険**と判断し、`ab738c9` で全削除した。お金の判断に使うアプリであるため。

**現在の状態**: `cards.json` は現金1件のみ、`bonuses.json` は空配列。`dataIntegrity.test.ts` は**優遇0件でもテストが通る**ように書かれている。

**次のAIへ**: 「アプリが空で寂しいから」という理由でサンプルデータを追加しないこと。**これは意図的な状態である。**

## 8-9. `src/core/` の独立を機械的に強制する

**何を決めたか**: `src/core/` に React・DOM・localStorage・通信を持ち込まないルールを、テストで自動検査する（`noUiDependency.test.ts`）。

**なぜその方式か**: `CLAUDE.md` の絶対ルール1（将来のReact Native移植のため）。人間のレビューに依存すると必ず破られるため、機械化した。

**副次的な設計への影響**: `estimateRewards` が**現在時刻を取得せず、`query.date` で受け取る**のはこのルールの帰結でもある。結果としてキャンペーンの期間判定がテスト可能になっている。

## 8-10. テスト構成をアプリ本体から分離する

**何を決めたか**: `tsconfig.test.json` を作り、`tsconfig.app.json` からテストファイルを `exclude` した。

**なぜその方式か**: `dataIntegrity.test.ts` が `node:fs` でJSONを読むため、Node.jsの型が必要。しかし `tsconfig.app.json` に `node` 型を足すと、**アプリ本体からもNode.js APIが使えてしまう**。これは `src/core/` の独立性を損なう。設定を分けることで、アプリ本体からNode.js APIを使えない状態を保っている。

## 8-11. 現金を比較の基準として扱う

**何を決めたか**: `PaymentKind` に `'cash'` を追加し、`baseRate: 0` の決済手段として登録する。

**なぜその方式か**: オーナーが持っている決済手段として「現金」を挙げたため。また、比較の基準（0%）として意味がある。

**特別扱い**: 現金のみ `source` を省略できる。`dataIntegrity.test.ts` は現金の `baseRate` が0であることを強制する。

## 8-12. GitHub Pages の base パス切り替え

**何を決めたか**: `vite.config.ts` で `process.env.GITHUB_PAGES === 'true'` のときのみ `base` を `/kessai-optimizer/` にする。

**なぜその方式か**: GitHub Pages のプロジェクトサイトはサブパス配信になるが、ローカル開発ではルート配信のほうが素直。環境変数はCIの `deploy.yml` でのみ設定している。

**注意**: `base` は PWA manifest の `start_url` / `scope`、Service Worker の `navigateFallback`、`loadPaymentData.ts` の fetch パスに波及する。**変更する場合はこの4箇所すべてを確認すること。**

## 9-1. 案A（カード×店舗の総当たり表）

## 9-3. 優遇が基本還元率を「置き換える」方式

**なぜ撤回したか**: 内訳の計算式（`基本0.5% ＋ 特約店1.0% ＋ イベント1.0%`）を画面に出せないため。オーナーの要望により足し合わせ方式へ変更。（詳細は8-3）

**なぜ撤回したか**: 8-8 参照。**この方針を再度採用しないこと。**

## 9-6. AIが公式サイトを直接読んで数値を集める

**なぜ駄目か**: [確認済み・実測] カード会社・小売のサイトは自動アクセスを拒否する。

| URL | 結果 |
| --- | --- |

**なぜ駄目か**: 97店舗分の公式URLを検証せずに書くと、リンク切れや誤リンクが混入する。「出典」を名乗る以上、検証できないものは書かないほうが誠実。`Store.source` を任意にすることで解決した。（詳細は8-7）

## 9-8. `noUiDependency.test.ts` がコメントを検査してしまった不具合

**症状**: ガードのテストを追加した直後、`reward.ts` が「localStorageを使っている」として検出された。

**原因**: `reward.ts` の冒頭コメントに「ここには画面のコードを一切書かない（React・DOM・**localStorage** を使わない）」という**説明文**が含まれており、正規表現がこれに一致していた。

**対処**: `stripComments()` を追加し、**ブロックコメントと行コメントを除去してから**検査するようにした。`://` を含む行（URL）は行コメントとして扱わないよう配慮している。

**教訓**: **ソースコードを文字列として検査するテストは、コメントを除外すること。** 同種のガードを追加する場合は必ずこの前処理を通す。

## 9-9. テストファイルが `tsc -b` を壊した

**症状**: `dataIntegrity.test.ts` を追加したところ、`npm run build` が `error TS2591: Cannot find name 'node:fs'` で失敗した。

**原因**: `tsconfig.app.json` の `types` が `["vite/client"]` のみで、Node.jsの型が無かった。

**対処**: `tsconfig.test.json` を新設し、`tsconfig.app.json` から `src/**/*.test.ts` を `exclude` した。（詳細は8-10）

**教訓**: `tsconfig.app.json` に `node` 型を安易に足さないこと。`src/core/` の独立性が損なわれる。

## 9-10. `public/Claude.md` という配置

**症状**: 開発方針のファイルが `public/` 配下に作られていた。

**なぜ駄目か**: `public/` の中身は**ウェブサイトとして配信される**ため、`https://.../Claude.md` で誰でも読める状態だった。またファイル名が `Claude.md` では、AIが自動で読み込む `CLAUDE.md`（全大文字）と一致しない。

**対処**: リポジトリ直下の `CLAUDE.md` へ移動し、`public/Claude.md` を削除した。

## 9-11. `CLAUDE.md` の「Vercelに自動デプロイ」という記述

**症状**: `CLAUDE.md` の技術構成に「Vercelに自動デプロイ」と書かれていたが、実際は GitHub Pages。**2回発生した**（1回目は修正後にオーナーが上書き、2回目も同様）。

**次のAIへ**: この記述が再びVercelに戻っていた場合、**実装ではなくドキュメント側の誤り**である可能性が高い。実際の配信は `.github/workflows/deploy.yml` を見て判断すること。ただしオーナーがVercelへ移行を意図している可能性もあるため、**勝手に判断せず確認すること。**

Vitest 導入時の動作確認用ファイル。`expect(1 + 1).toBe(2)` のみ。ファイル冒頭に「本物のロジックを書いたら削除して構わない」と明記してある。**削除して問題ない。**

## 後回しでよいもの

### 11-3. 暫定実装: 決済手段の登録UI

10-7 参照。**オーナーと合意済みの暫定実装。** 勝手に作り替えず、Priority 4 のタイミングで対応すること。

### 11-4. 1カードにつきチャージ元を1つしか選べない

`OwnedPayment.chargeFromCardId` は単一値。「PayPayをAカードからチャージした場合」と「Bカードからチャージした場合」を同時に比較できない。

**意図的な簡略化**（UIを単純に保つため）。比較したい要望が出たら、`OwnedPayment` を複数エントリ持てるようにする（`RewardBreakdown` は既に `chargeFromCardId` を保持しており、`RewardList` の key もそれを含むため、**計算側は複数エントリに対応済み**）。

### 11-5. エラーハンドリングの粒度

`loadPaymentData` は3ファイルのうち1つでも失敗すると全体が失敗し、画面全体がエラーになる。部分的な復旧は行わない。

**意図的**: 中途半端なデータで誤った還元率を表示するより、明確に失敗させるほうが安全という判断 [推測: 明示的な議論はしていないが、「実際より高く見積もらない」方針と整合する]。

### 11-6. 型安全性

`estimateRewards` は `PaymentData` を受け取るが、**JSONの実行時検証は行っていない**（`as` によるキャスト）。実行時の検証は `dataIntegrity.test.ts`（CI）に委ねている。

**意図的**: zod 等のバリデーションライブラリを入れると依存が増える。CIで形式が保証されるため、実行時検証は冗長という判断 [推測]。

**ただし**: オーナーがGitHub上で直接JSONを編集し、CIが赤いままマージした場合は実行時に壊れる可能性がある。ブランチ保護ルールの設定は**未確認**。

### 11-7. パフォーマンス

`estimateRewards` は `owned` の各カードについて `data.bonuses` を全走査する。O(カード数 × 優遇数)。データ規模（カード数十件・優遇数百件程度）では問題にならない。**最適化は不要。**

`searchStores` も全店舗を走査する。97件では問題ない。

### 11-8. `App.css` / `index.css` のCSS変数

テーマ変数は `index.css` の `:root` と `@media (prefers-color-scheme: dark)` に定義。コンポーネント固有のスタイルは `App.css` に集約されている。ファイル分割はしていない。

**現規模では妥当。** コンポーネントが増えたら CSS Modules 等を検討する余地がある。

### 11-9. スケーラビリティ

店舗データが数千件規模になると、全件を1つのJSONで配信するのが重くなる。現在97件では問題ない。

# 20. 30秒版引き継ぎ

**このプロジェクトは何か。**
店名を入れると、自分が持っている決済手段のうちどれで払うのが得かを、還元率の高い順に内訳付きで示すPWA。「普段行かない店に入ったとき、辞書のように引く」用途を想定している。サーバーもDBも認証もなく、GitHub Pages で配信される静的サイト。データは `public/data/` のJSON、ユーザー設定は localStorage のみ。オーナーはプログラミング未経験で iPad のブラウザのみで作業しており、**「テストが通ること」が唯一の検証手段**である。この制約があらゆる技術判断の根拠になっている。

**現在どこまで完成しているか。**
機構はすべて完成している。かな予測検索（濁点・略称・カタカナ対応）、還元額の計算（二重取り・付与上限の頭打ち・期間限定キャンペーン・金額有無での順位切替）、内訳と出典の表示、PWAのオフライン動作、CI、自動デプロイ。テストは69件すべて成功し、**テスト自体が機能することも10通りの意図的な破壊で検証済み**。店舗データは97件・8分類を登録済み。

**最大の課題は何か。**
**本物の還元率データが1件も入っていない**こと。決済手段は現金1件のみ、優遇は0件。開発初期に構造確認用の架空の数値を入れていたが、誤情報の危険があるため全削除した。さらに問題なのは、**その削除がまだ `main` にマージされておらず、公開中のサイトには架空の数値が表示され続けている**こと。加えて、AIはカード会社の公式サイトを読めない（403で拒否される）ため、数値の収集はオーナーの手作業に依存する。

**次に何をすべきか。**
Priority 1: 未マージの2コミットをPRにしてマージする（架空データの削除を公開に反映）。Priority 2: オーナーから調査結果を受け取り、5つの決済手段（現金・PayPay・三井住友Olive・JCBカードW・イオンカード）のデータを投入する。Priority 3: 対象店舗が名指しの制度を、カテゴリ指定ではなく店ごとの指定に切り替える（過大評価を防ぐため）。

**絶対に壊してはいけない設計判断は何か。**
① `src/core/` にReact・DOM・localStorage・通信を持ち込まない（React Native移植のため。テストが機械的に強制している）。② 還元率は「0.1%を1とする整数」で持つ。③ 優遇は足し合わせ、ただし特約店は最大1つ・キャンペーンは全加算という非対称性は意図的。④ `rateBasis`（add / total）で数字の意味を明示し、基本還元率の二重計上を防ぐ。⑤ 端数は切り捨て、不明な要素は加算しない（**実際より高く見積もらない**）。⑥ 確認できていない数値をデータに置かない。⑦ 「目安」であることと上限の前提を示す注意書きを消さない。⑧ データはコードに書かず `public/data/` のJSONに置く。
