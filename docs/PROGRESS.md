## 決めたことと理由

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| データ構造 | 案B（店 / 分類で対象指定） | 案Aは「コンビニ全般」が書けず更新漏れが必ず起きる。案Cは手で書くには難しすぎる |
| 還元率の持ち方 | 0.1%を`1`とする整数 | 小数計算のずれを避ける。0.1%単位に丸める方針とも一致 |
| 優遇の合成 | 当てはまるものを足し合わせる | 画面に計算式を出すため。実際の制度もキャンペーンは上乗せが多い |
| 数字の書き方 | `add` / `total` の2通り | 公式サイトの数字をそのまま写せるように。引き算はアプリ側で行う |
| 特約店の重複 | 店指定が分類指定に勝ち、1つだけ採用 | 両方足すと過大評価になる |
| 端数 | 切り捨て | 四捨五入だと実際より多く見せてしまう |
| 出典 | 還元率には必須。店名・現金には不要 | 根拠が要るのは「数値の主張」だから |
| 仮の数値 | 置かない | お金の判断に使うため。確認できたものだけを載せる |

## 認識している問題点

### 高

- **公開中のサイトに仮の還元率が残っている。** 「三井住友カードでコンビニ7%」などは架空の値。
  仮データを削除した変更が未取り込みのため。最優先で取り込む。
- **本物の還元率が1件も入っていない。** 対象は PayPay / 三井住友Olive / JCBカードW / イオンカード。

### 中

- **Claudeは公式サイトを読めない。** カード会社のサイトは自動アクセスを拒否する（全て403）。
  Web検索はできるが又聞き情報のため出典にできない。数値収集は人手に頼る必要がある。
- **分類まるごとの指定は過大評価になりうる。** 対象店舗が名指しの制度では、店ごとに登録すること。
- **上限計算は「その月にまだ使っていない」前提。** 画面に注意書きで対処済みだが仕組み上の限界。
- **ポイント価値が1円でないカードの扱いが未定義。** JCBのOki Dokiポイントなど。間違えると数倍ずれる。

### 低

- 決済手段の登録画面がチェックボックスのまま（件数が増えると破綻する）
- 画面のテストがない
- 最終確認日が古くなったことを知らせるしくみがない
